# Purpose-first site generation

## Source

Synced from Linear Containment Protocol project resource (2026-05-12). Git is canonical for ongoing edits. Original: [Linear doc](https://linear.app/spectranoir/document/purpose-first-site-generation-cfa80d806a7b).

## Scope

Covers purpose-first site generation where intended function drives hazards, room families, traffic, security behavior, ingress assumptions, and legacy overlays before geometry is finalized.

## Included issue boundary

- SPE-395

## Core rules

- A site begins from a declared purpose packet rather than from geometry alone.
- Purpose should drive expected room families, hazard profiles, guard behavior, ingress types, and failure modes before map resolution.
- Current active function and buried or legacy substratum may both affect generation.
- Generated outputs should remain legible in metadata, recon, and authoring/debug surfaces.

## Packet structure

- Purpose packets should encode builder assumptions, location assumptions, ingress assumptions, topology tendencies, hazard families, treasure or asset logic, inhabitant expectations, and spatial profile cues.
- The system should support active-site-over-legacy cases where industrial, ritual, civic, predatory, or covert functions coexist asymmetrically in one site shell.
- Public anomaly reports may trigger a bounded hostile-site investigation without turning the whole city into the active map.

## Purpose and deception

- Some sites should rely on false sanctums, duplicate treasures, fake goals, false victories, or secret servant logistics while still preserving discoverable truth surfaces.
- Sites may preserve visible splendor or ordinary civic identity while concealing deeper hostile or restricted layers.
- Ingress and route truth can be hidden under public-facing geometry.
- Purpose packets should derive present room palettes, hazards, and clue surfaces from original function rather than from underground status or generic dungeon shape.
- Legacy function and current use should both remain able to shape one site packet, so temples turned lairs, citadels turned squats, mines turned oracle ruins, and civic sites turned covert infrastructure preserve meaningful before/after logic.

## Portability and layering

- Some site packets should be terrain-portable, preserving core interior logic while swapping a small number of surface ingress or weather variables.
- Portability notes should identify which packet variables are structural constants versus region-specific swaps.
- Strong site packets should support multiple hook classes at once such as rumor, rescue, lore-hunt, invitation, and survival pressure rather than one prescribed entry motive.
- Vertical sacred stacks, layered institutions, hostile compounds over civic ruins, and active extraction over older buried hostile layers should all remain supportable under one purpose-first framework.
- Mansion-scale hostile sites, tombs, and apex lairs may combine covert ingress, locked-room layers, hidden circulation, false specimen displays, concealed remains, decoy sanctums, and servant logistics within one bounded packet.

## Distinctions to preserve

- Purpose is not cosmetic flavor added after map generation.
- Legacy function is not erased by current use.
- Metadata-first generation does not require local lore density at every node to carry operational meaning.
- Libraries, archives, ritual objects, grave goods, and room-use signals can be strategic power surfaces in themselves, not only decorative content.

## Non-goals

- No full architect simulator.
- No sprawling planning logic.
- No assumption that map shape comes first and purpose is added later.

## Expected use

Use this doc when designing any site whose operational identity, hazard ecology, ingress behavior, and internal logic should be derived from what the place is for before exact geometry is laid out.

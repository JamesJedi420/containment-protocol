## Boundaries to check before acting

1. **Separate operations from authority.** Creating a repository file is not creating a Linear issue. Reading a source does not grant mutation access. Linear remains the planning/lifecycle record; GitHub code, PRs, tests, and CI provide implementation evidence.
2. **Identify the active agent and its permissions.** Tools, connectors, credentials, branch protection, workspace policy, and task assignments can restrict otherwise permitted actions. Do not treat an aspirational capability as proof that it works in the current session.
3. **Preserve one canonical CP/Academy owner.** Shared developer-governance capabilities have one CP-owned implementation. Academy consumes the shared system, not a parallel authority or toolchain.
4. **Keep policy and handoff distinct.** This document summarizes standing capabilities only. For an approved implementation session, use the [agent session handoff](agent-session-handoff.md) and the existing structured freshness/continuity boundary [SPE-3337](https://linear.app/spectranoir/issue/SPE-3337); confirm the current issue, parent, branch, blockers, and evidence rather than relying on this static card.
5. **Do not infer shipped enforcement.** The [governance authority contract](governance/authority-contract.v1.json) is a policy projection, not a universal interception of external connector writes. Existing [SPE-3271](https://linear.app/spectranoir/issue/SPE-3271) owns broader active-document conformance; [SPE-3348](https://linear.app/spectranoir/issue/SPE-3348) owns validation selection. This card creates neither a second conformance engine nor a new authorization rule.
6. **Escalate genuine conflicts.** Missing authorization, incompatible current policy, tool limitations, or consequential product-direction decisions cannot be resolved by assuming a table entry overrides higher authority.

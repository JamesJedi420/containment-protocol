# Hermes shipping checkpoints

Codex/Cursor dispatch Hermes automatically at the checkpoints below during an authorized shipping loop. This is an agent-driven CLI workflow, not a scheduled job or a Git hook. The coding agent owns decisions, fixes, validation, git operations, PRs and Linear lifecycle updates. Hermes returns evidence and drafts only.

## Local-model delegation policy

Hermes uses the user's local Qwen3.5 9B. Preserve its configured model/provider; do not switch to a paid provider or change configuration. Favor delegation when it compresses substantial evidence into a short, verifiable result. This can reduce paid Codex context; it does not guarantee measured savings.

- Delegate large CI/build logs, multi-document comparisons, external research and first-pass review-comment triage. Give Hermes the exact question, relevant paths/log locations and approved boundary instead of copying the full conversation or asking it to read the whole repository.
- Ask for a compact evidence packet, normally at most 500 words: findings ranked by relevance, exact file/line or log anchors, source URLs/dates for external claims, command exit codes when available, unknowns and suggested next checks. No full log dumps or unsupported conclusions.
- Run simple validators and short targeted searches directly as Codex/Cursor. Supply their output locations to Hermes only when interpretation requires substantial reading. Documentation checkpoints still apply: the coding agent runs required validators, and Hermes handles substantial comparison/triage work when present.
- Before implementation, delegate acceptance-to-code/test mapping when the approved boundary spans substantial evidence; Hermes identifies candidate gaps without selecting implementation scope. On CI failure, delegate large-log diagnosis. After review feedback, delegate grouping duplicates and checking claims against source when the feedback is substantial. Documentation-drift and release-summary tasks use the same size/relevance test.
- Codex/Cursor inspect the cited evidence needed to confirm material claims and perform final review. Do not repeat the entire delegated reading by default; expand inspection when uncertainty, contradictions or missing anchors justify it. Hermes output is untrusted evidence, never approval or proof of correctness.
- At every checkpoint, assess applicability. For small tasks record `direct — delegation overhead exceeds evidence volume` and perform the check directly; do not launch Hermes for a one-line result or ceremonial acknowledgment. Record `not applicable` for absent research/triage needs. Do not duplicate successful checks on unchanged inputs.
- If one bounded attempt fails or returns unsupported findings, stop retry loops and inspect the required evidence directly. Retry only when new information addresses the failure. Retain a short session-ID/source reference instead of importing the full Hermes transcript into Codex context.

### Verification after research and policy-review tests

Codex/Cursor retain external retrieval by default and provide Hermes a bounded primary-source packet for synthesis. Hermes independent retrieval remains a separately assigned capability probe until an observed trace proves actual tool identity, working source URLs, correct dates/exceptions and honest limitations. A fluent report, process exit 0 or self-reported tool name does not meet this gate. Record a pass only for the specific tested tools/question, not all future research.

For research and policy reviews, Codex/Cursor verify every material conclusion against the cited passage before accepting it, including a clean/no-change verdict. Policy contradictions require both source anchors and exact conflicting text; a missing comparison remains unverified. Reuse successful unchanged evidence. Keep failed findings rejected rather than silently promoting them into policy or scope decisions.

Record available input/output token totals, elapsed time and correction/review effort with each capability test. Missing usage fields are unknown; report observed cost and overhead without inventing a counterfactual direct-work baseline. Expand delegation only when repeated verified results justify the total retrieval, synthesis and verification cost.

## Autonomous Agent Orchestration (`autonomous-ai-agents`)

**Triggers:** multiple independent analyses within an authorized boundary, comprehensive project health checks, or coordination between inspection, Git analysis, research and test-validation skills. This is on demand; a small docs edit or one failing assertion does not justify a multi-agent audit.

**Routing:** Codex/Cursor define scope and retain final judgment. Hermes may coordinate explicitly assigned read-only analysis workers and aggregate findings using the configured local Qwen3.5 9B. Prefer local evidence gathering and synthesis over spawning additional paid coding agents. Hermes oversight is analytical coordination; it does not grant implementation, publication, git mutation or Linear authority to any worker.

The installed `autonomous-ai-agents` directory is a category, with `DESCRIPTION.md` and child skills such as `codex/SKILL.md` and `hermes-agent/SKILL.md`, rather than a single top-level `SKILL.md`. Discover it under the installed Hermes skills root and load only the child skill needed for the actual worker. Do not assume `--skills autonomous-ai-agents` resolves or that Codex/Cursor tools and authentication are available inside Hermes. Repository restrictions override generic skill examples for installations, bypass flags, commits and PRs.

1. **Define scope.** Record the question, approved issue/slice when present, repository path, HEAD/base SHAs, dirty state, included paths and exclusions. For an unowned read-only health review, record that boundary without manufacturing an issue. Specify a task graph with independent workers and sequential dependencies, exact input artifacts, per-worker output limits, a concurrency cap and a total time/turn budget. Start with at most two local analysis workers; increase only when observed capacity and useful independent work justify it. Local inference may serialize or slow under load, so parallel execution is not assumed to improve latency or token use.
2. **Assign bounded workstreams.** A health check can split into codebase inspection, Git history/divergence analysis and test-evidence review. Run independent work within the cap; aggregate only after required results arrive. Codex/Cursor run short Git diagnostics and select/run required tests and validators directly, then provide revision-anchored artifacts for substantial Hermes interpretation. Research uses the existing retrieval gates; dependency evidence still starts with direct Sonatype checks. Workers share no mutable browser/save state or output paths; serialize validation runs that contend for caches or generated artifacts. Freeze inspected files until the run completes and reject stale results after material input changes.
3. **Constrain delegation.** Every worker inherits the same read-only boundary, source restrictions, budget and evidence format. The default dispatch below still prohibits delegation. For an orchestration dispatch only, replace that prohibition with a named worker allowlist, maximum fan-out and explicit stop condition; all other restrictions remain. Workers may not delegate further. Assigning work to a Codex/Cursor worker requires explicit coding-agent assignment of that worker, its task, cost boundary and available interface; do not silently launch paid CLIs or message existing chats. If the required orchestration capability is unavailable, record it and use sequential bounded analysis or the direct fallback; never claim workers ran from a skill description alone.
4. **Aggregate evidence.** Hermes deduplicates findings and returns one report of at most 500 words: worker/task status, inspected revision, ranked findings with file/line or artifact anchors, actual commands/exit codes, disagreements, unknowns and suggested next checks. Keep detailed logs in separate named artifacts. Include failed, timed-out and unperformed workstreams; completion of one worker is not completion of the audit. Cancel remaining workers on budget exhaustion or invalidated inputs before retrying. Record actual worker/session IDs and observed tool access.
5. **Verify and act.** Codex/Cursor verify material anchors, resolve contradictory conclusions and apply only separately authorized actions. Reuse unchanged evidence across skills instead of asking each worker to reread the repository. Record available local/paid token totals, elapsed time, dispatch and correction effort; unknown usage remains unknown. Claim savings only with a comparable measured baseline. This workflow preserves existing independent review, CI, Linear ownership and new-session closeout requirements.

Flow: bounded scope → task graph and budgets → independent analysis workers → Hermes evidence aggregation → Codex/Cursor verification and authorized action.

## Codebase Inspection (`codebase-inspection`)

Use before major refactoring discussions, when assessing subsystem size or complexity trends, and when checking whether proposed changes are appropriately scoped. This is an on-demand evidence workflow, not a required full-repository scan for every slice.

**Routing:** Codex/Cursor run short, targeted counts directly. Delegate substantial repository inventories, subsystem comparisons and first-pass hotspot triage to Hermes Desktop through the existing one-shot CLI procedure below. Preserve the configured local Qwen3.5 9B. The purpose is to compress large evidence into a compact report; token savings are expected only when the avoided reading exceeds dispatch and verification overhead, and must not be claimed as measured without accounting.

1. Capture HEAD/base SHAs, dirty-worktree state and the question or approved slice boundary. Choose relevant tracked source paths; exclude dependencies, build outputs, generated files and vendored code. Report tests, fixtures and documentation separately from application source. Name exclusions and any deliberately included untracked paths.
2. Check whether `pygount` is already available and read its installed CLI help before selecting options. Run it over the selected paths to obtain per-file and per-language source LOC. If unavailable, report that limitation; do not install it as part of inspection. Any later tool installation requires the repository's Sonatype dependency review. A fallback count must name its method and must not be presented as pygount output.
3. Report language distribution as source LOC and percentages of the same included source-LOC total, including TypeScript and CSS when present. Group totals by relevant subsystem. Record tool version, commands, exit codes, counting definition and exclusions so results can be reproduced.
4. Rank the largest files as **size hotspots / complexity candidates**. LOC does not measure cyclomatic or cognitive complexity. Inspect a bounded shortlist for concrete concerns such as branching, coupled responsibilities or repeated orchestration; cite file/line evidence. Only label a metric as measured complexity when a separate available analyzer produced it, and name that analyzer and metric.
5. For trends, compare against an existing baseline with matching tool version, paths, exclusions and counting definition. Without a comparable baseline, report a snapshot rather than a trend. For scope checks, relate the changed paths to the approved boundary; size alone neither proves scope fit nor authorizes a refactor.
6. Hermes returns at most 500 words: revision/scope, LOC and language table, subsystem totals, a short ranked hotspot list with anchors, baseline deltas when comparable, unknowns and suggested verification. Keep detailed output in a named local artifact and return its path instead of dumping it into Codex context. Use the dispatch restrictions below; normal inspection reports may be generated locally, but repository source and configuration remain read-only.
7. Codex/Cursor verify material counts and cited source evidence, then prioritize within the authorized boundary. Hermes proposes candidates only; inspection does not authorize implementation, backlog changes or new dependencies. Reuse results while inputs remain unchanged. On failure, follow the direct-check fallback below and identify unperformed checks.

Flow: select scope → pygount → LOC/language/subsystem totals → candidate hotspot evidence → compact Hermes report → Codex/Cursor verification and prioritization.

## Testing & Debugging Support: Systematic Debugging (`systematic-debugging`)

**Triggers:** use when tests fail and the cause needs investigation, when Cursor reports an issue and needs direction, or when QA identifies a bug whose implementation is deferred. These are agent-initiated workflow triggers, not scheduled jobs or Git hooks. Analysis can proceed read-only without authorizing a fix.

**Routing:** Codex/Cursor perform small reproductions, short log checks and targeted validation directly. Delegate substantial diagnostic logs, code-path tracing and first-pass root-cause pattern analysis to Hermes Desktop through the one-shot dispatch procedure below. Use the configured local Qwen3.5 9B and a bounded question with exact paths and log artifacts; return compact evidence rather than full logs. Delegation aims to reduce paid context, but token savings are not measured unless accounting exists. Codex/Cursor retain final diagnosis, scope, fix implementation and verification authority.

### Phase 1 — Understand the bug before fixing

Record expected versus observed behavior, exact reproduction steps or failing test names, command and exit code, repository revision, dirty-worktree state and relevant runtime/environment details. Preserve diagnostic output in a named local artifact. Identify whether the failure is new, pre-existing or unknown; do not infer causation from the latest edit alone. For simulation failures, capture the seed, action sequence and relevant persisted-state/schema version when available. If reproduction is unavailable, say so and distinguish the QA report from verified behavior.

### Phase 2 — Find the cause with evidence

Trace the failing assertion or visible symptom through the relevant caller, projection/store/domain boundary and state transition. Separate observations from hypotheses; rank candidate causes and cite exact file/line and log anchors. Propose the smallest discriminating check and record its result when performed. Distinguish environment/tooling failures from application defects. Hermes may run existing targeted tests under the dispatch restrictions and return evidence, but must not modify source, tests or configuration to test a hypothesis. Codex/Cursor verify material anchors and the causal explanation before treating a candidate as the root cause; unresolved causes remain explicitly unknown.

### Phase 3 — Plan the fix

Hermes may draft the smallest candidate fix and a regression-test approach in prose. Codex/Cursor assess the verified cause against the approved issue/slice boundary, architecture, determinism and persistence requirements, then select and implement the authorized fix. Do not weaken assertions, silence diagnostics or expand scope to obtain a green result. If QA implementation is deferred, stop at an evidence handoff: reproduction, verified facts, ranked hypotheses or confirmed cause, proposed check/fix, existing owner if known and reactivation condition. Mark implementation and fix verification as deferred, not complete. Do not create new scope or claim resolution from diagnosis alone.

### Phase 4 — Verify the fix

Codex/Cursor demonstrate that the original reproduction or meaningful regression test fails before the fix and passes after it when feasible, then run the most specific affected tests and required lint/validators. Follow repository rules for broader coverage, including the full suite for non-trivial simulation changes. Record actual commands, exit codes and remaining limitations. Hermes can summarize substantial verification output and identify residual concerns, but its report does not replace the coding agent's validation. If the original reproduction cannot be rerun, distinguish passing checks from an unverified resolution claim.

**Hermes evidence packet:** normally at most 500 words covering symptom/reproduction, inspected revision and paths, diagnostic commands/exit codes, causal trace with anchors, facts versus hypotheses, smallest suggested fix/check, and unknowns or deferred verification. Keep detailed logs in named artifacts. Supply explicit executable paths, shell and bounded helper commands when needed; prior inspection testing showed that implicit Python lookup and Windows path matching can fail. Never count a process launch or plausible explanation as completed debugging. On failure, use the bounded direct fallback in this document rather than repeating unchanged attempts.

Flow: failing test / Cursor report / QA finding → diagnostic evidence → causal trace → Codex/Cursor fix plan → authorized implementation → regression verification; deferred implementation ends with a truthful diagnostic handoff.
